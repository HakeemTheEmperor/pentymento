# PTM-5001: capture-gap

```text
✗ prod-pg: a gap in captured log after 1/0/3000060: the replication slot pentym_prod_pg was invalidated (max_slot_wal_keep_size), and the WAL it held was removed
  point-in-time recovery cannot reach a time inside the gap until a new base backup is taken
→ pentym backup prod-pg
```

## Cause

Some of the database's log was never stored, and the server no longer has it:

- **Postgres:** the replication slot was dropped, or the server invalidated it because it held more WAL than `max_slot_wal_keep_size` allows, or the server removed WAL the slot should have kept.
- **MongoDB:** the oplog rolled over: its oldest entry is newer than the last one pentym stored, because capture was stopped or behind for longer than the oplog reaches back.

The agent and `pentym catch-up` record the gap in the repository and the journal, from the last stored position to where capture could resume.

## Impact

Point-in-time recovery cannot reach a time inside the gap. Snapshots, and recovery to times before the gap, are not affected. Capture continues from where the server stands, but recovery to times after the gap needs a snapshot taken after it: the agent takes one by itself; after `pentym catch-up`, take one.

## Fix

Run `pentym backup <target>` (the agent does this by itself when it finds the gap). Then make the gap less likely to happen again:

- Keep an agent running, or two for failover, so capture does not stop for long.
- Postgres: keep `max_slot_wal_keep_size` large enough to hold the WAL written during the longest outage you expect.
- MongoDB: enlarge the oplog with `replSetResizeOplog` so its window (`pentym_mongo_oplog_window_seconds`) covers that outage; the agent warns when it is under 24 hours.
